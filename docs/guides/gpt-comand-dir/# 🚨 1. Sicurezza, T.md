# 🚨 1. Sicurezza, Threading e Resilienza (Priorità Alta)

## 1.1 — `httpx.Client()` creato/distrutto per ogni request → overhead + rischio leak silenziosi

Hai un pattern ripetuto:

```python
with httpx.Client(...) as c:
```

sia in `clients/anythingllm.py` che in `core/ai_tasks.py`.

Problema:

- ogni chunk crea socket/TLS pool nuovi
- su workload lunghi puoi accumulare TIME_WAIT/socket exhaustion
- Windows è particolarmente fragile qui
- il kill switch chiude client “in volo”, ma il lifecycle è troppo granulare

### Fix consigliato

Passa a:

- un client singleton thread-safe per backend
- pool connection limitato
- timeout granulari

Esempio:

```python
HTTP_LIMITS = httpx.Limits(
    max_connections=20,
    max_keepalive_connections=10,
)

HTTP_TIMEOUT = httpx.Timeout(
    connect=10.0,
    read=600.0,
    write=30.0,
    pool=30.0,
)

shared_client = httpx.Client(
    timeout=HTTP_TIMEOUT,
    limits=HTTP_LIMITS,
    headers=_headers(),
)
```

Poi registri SOLO request attive nel kill switch, non l’intero client.

## 1.2 — Race condition potenziale su registry client del kill switch

Hai:

```python
state.register_client(client)
state.unregister_client(client)
```

Non vedo il codice interno, ma se usi:

- `set()`
- `list()`
- dict mutabile

senza lock dedicato → race condition reale.

### Criticità

Il kill switch può iterare i client mentre un worker:

- registra
- deregistra
- chiude

=> `RuntimeError: set changed size during iteration`  
oppure client zombie non chiusi.

### Fix

Dentro orchestrator:

```python
self._clients_lock = threading.RLock()
self._clients: set[httpx.Client] = set()
```

e:

```python
with self._clients_lock:
    snapshot = list(self._clients)
```

mai iterare direttamente la struttura mutabile.

## 1.3 — Flask SSE: memory leak classico se non pulisci subscriber morti

Hai SSE realtime log stream.

Rischio enorme:

- browser refresh multipli
- EventSource zombie
- generatori mai chiusi

Se usi una lista globale di queue subscriber:

```python
subscribers.append(q)
```

e non fai cleanup robusto → leak progressivo.

### Sintomi

Dopo ore:

- RAM sale lentamente
- log delay
- CPU polling
- queue bloccate

### Fix minimo

Nel generator SSE:

```python
try:
    while True:
        yield ...
finally:
    orchestrator.remove_subscriber(q)
```

E imponi:

- max queue size
- timeout heartbeat
- cleanup inattivi

## 1.4 — Flask dev server in produzione desktop = ok-ish ma fragile

Hai:

```python
flask_app.run(threaded=True)
```

Per desktop locale va bene.

MA:

- SSE + thread multipli + long polling
- Flask built-in server
- pywebview

= combinazione instabile sul lungo periodo.

### Consiglio reale

Passa a:

- `waitress` su Windows
- oppure `hypercorn`

Esempio:

```python
from waitress import serve
serve(app, host="127.0.0.1", port=7842, threads=8)
```

Molto più stabile per SSE.

## 1.5 — `time.sleep()` ovunque → shutdown lento e semi-deadlock

Hai cooldown con:

```python
time.sleep(...)
```

Problema:  
il kill switch non interrompe sleep.

### Fix corretto

Sostituisci con:

```python
stop_event.wait(timeout)
```

Esempio:

```python
if stop_event.wait(PIPELINE_LM_COOLDOWN_S):
    raise InterruptedError("Stopped")
```

Shutdown immediato.

## 2.2 — Sliding Window rischia “context poisoning”

Hai:

>
> passing condensed context to next chunk
>

Ottima idea.

Ma rischio:

- errore chunk N
- propagazione errore fino a N+100

Classico drift cumulativo.

### Soluzione migliore

Non passare SOLO summary cumulativo.

Usa:

```text
[GLOBAL MEMORY]
+ ultimi 2 summary
+ facts canonici
+ current chunk
```

Architettura:

- rolling facts
- not rolling prose summary

Molto più stabile.
